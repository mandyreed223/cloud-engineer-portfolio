🧠 Things My Projects Have Taught Me

The technical skills matter, but the strongest lessons come from understanding what the system is doing, why it failed, and how it recovered. 😅

☁️

Deployment Is Only Step One

A successful deployment does not automatically mean the application actually works. Terraform can successfully create infrastructure while the application running inside it is still unhealthy. I validate the infrastructure and the application path.

🔗

Infrastructure Is a Chain of References

Terraform became easier to understand when I stopped viewing resources as isolated blocks and started following values between them. VPC IDs, subnet IDs, Security Groups, Target Groups, Launch Templates, IAM roles, and Auto Scaling Groups connect individual resources into a complete architecture.

🔎

Follow the Entire Path

Troubleshooting gets easier when I understand how every service connects. Whether the path crosses an ALB, Target Group, EC2 and Apache, or Docker, ECR, Kubernetes and AWS load balancing, following the request from beginning to end helps isolate the failing layer.

🧩

Tiny Errors Can Break Big Architectures

One leading space before a User Data shebang was enough to stop Apache from installing, fail ALB health checks, and cause Auto Scaling to repeatedly replace unhealthy instances. Small configuration mistakes can have architecture-wide effects.

🔐

Secure It, Then Prove It

Private instances do not automatically require inbound SSH. AWS Systems Manager Session Manager gave me secure diagnostic access without public IP addresses, port 22, or SSH key management. Least privilege matters more when I validate that it actually works.

♻️

Desired State Is Something You Can Test

Docker Swarm, Kubernetes, and EC2 Auto Scaling all reinforced the same idea at different layers: define the state you want, deliberately change reality, and observe how the platform responds. When I terminated a healthy EC2 instance, Auto Scaling restored the desired capacity without manual intervention.

☁️

Kubernetes and AWS Operate at Different Layers

EKS helped make the boundary much clearer. Kubernetes manages workloads, desired state, Services, rolling updates, and Pod autoscaling, while AWS provides the compute, networking, load balancing, container registry, managed control plane, and logging underneath it.

📈

Scaling Happens at Different Layers

Kubernetes can scale application Pods while EC2 Auto Scaling changes infrastructure capacity. Understanding which layer is scaling, why it is scaling, and what signal drives the change makes the behavior much easier to reason about.

💾

Persistent Data Changes Everything

Containers may be disposable, but application data is not. Shared storage, database placement, and recovery behavior need to be considered as part of the architecture.

🔗

Healthy Infrastructure Does Not Guarantee a Healthy Application

An EC2 instance can be running while the application inside it is unusable, just as a Kubernetes Pod can show Running while the complete application path is broken. Health needs to be evaluated at the layer that actually matters to the application.

🔄

Versioning Makes Changes Easier to Understand

Versioned ECR images made Kubernetes releases easier to follow, while Launch Template versions made infrastructure changes explicit. After correcting EC2 User Data, Instance Refresh rolled the new Launch Template configuration across the Auto Scaling Group.

🧹

Clean Up Counts Too

Building cloud resources is fun. Knowing how to safely tear them down is part of understanding the full lifecycle, especially when environments include networking, NAT, load balancing, Auto Scaling, EC2, EKS, ECR, and CloudWatch resources.
